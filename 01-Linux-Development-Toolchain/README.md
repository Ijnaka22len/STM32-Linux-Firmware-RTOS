# Stage 01 - Linux-Based STM32 Development & Debugging

## Overview

I established a native **Debian GNU/Linux 13** development workflow for the **STM32 NUCLEO-F446RE**, covering firmware authoring, cross-compilation, linking, programming, verification, and hardware debugging. The development host runs Linux; the STM32F446RE executes a standalone ARM Cortex-M4 bare-metal application, **not the Linux kernel**.

The reference application configures the onboard green **LD2 LED (PA5)** through memory-mapped registers and repeatedly toggles its output. No STM32CubeIDE, HAL, or RTOS is required for this experiment.

**Validation status:** The repository's Stage 01 example was built and programmed on the target board **STM32: NUCLEO-F446RE**. OpenOCD reported successful programming, verification, and reset. Continuous LD2 blinking was also verified during the preceding equivalent bare-metal experiment.

### Hardware connection

I connected the NUCLEO-F446RE's **ST-LINK USB connector** to the Linux host using a data-capable USB cable. The onboard ST-LINK connects to the STM32 through SWD; no external SWD wiring or LED circuitry was required.

## 2. Install the host toolchain

I installed the cross-compiler, binary utilities, OpenOCD, GDB, and supporting command-line tools using Debian packages:

```bash
sudo apt update
sudo apt install -y \
  build-essential gcc-arm-none-eabi binutils-arm-none-eabi \
  openocd gdb-multiarch git tree usbutils
```

I verified the installed toolchain with:

```bash
arm-none-eabi-gcc --version
arm-none-eabi-objcopy --version
openocd --version
```

`arm-none-eabi-gcc` generates machine code for the bare-metal ARM target. It does **not** compile a Linux executable for the host architecture.

## 3. Confirm USB and SWD connectivity

I checked that Linux enumerated the ST-LINK interface:

```bash
lsusb
lsusb -d 0483:
```

The probe appeared as `0483:374B STMicroelectronics ST-LINK/V2.1`.

I then launched OpenOCD:

```bash
openocd -f interface/stlink.cfg \
  -c 'transport select swd' \
  -f target/stm32f4x.cfg
```

OpenOCD identified the Cortex-M4 processor, successfully examined the target, and opened a GDB server on TCP port **3333**. I stopped this test server using `Ctrl+C` before starting a separate flashing operation; concurrent OpenOCD servers can compete for the same ST-LINK interface.

### Firmware source: `Core/main.c`

The application enables the GPIOA peripheral clock through `RCC_AHB1ENR`, configures PA5 as a push-pull digital output using `GPIOA_MODER`, `GPIOA_OTYPER`, and `GPIOA_PUPDR`, and changes the output state using the atomic GPIO bit-set/reset register (`GPIOA_BSRR`).

The LED is driven high and low in a continuous loop. The software delay uses an instruction-count loop; it is **not calibrated to milliseconds**, and its duration depends on clock configuration and compiler optimization.

### Reset and startup: `Core/startup.c`

The Cortex-M vector table begins with the initial main stack pointer and the address of `Reset_Handler`. The reset handler copies initialized `.data` values from flash to RAM, clears `.bss`, and calls `main()`.

This is a **minimal polling-only startup implementation**. Its external interrupt vectors point to a default infinite-loop handler. It is not the official STM32F446RE device vector table and does not implement peripheral interrupt dispatch or FreeRTOS exception integration.

### Memory layout: `STM32F446RE.ld`

| Region | Start address | Size | Purpose |
|---|---|---|---|
| FLASH | `0x08000000` | 512 KiB | Vector table, program instructions, constants |
| SRAM | `0x20000000` | 128 KiB | Stack and writable data |

The linker script defines `_estack`, `_sidata`, `_sdata`, `_edata`, `_sbss`, and `_ebss` for reset-time initialization. This small example does not reserve a separately measured stack budget; more complex firmware requires stack and heap analysis.

## 5. Compile and inspect firmware

From the repository root, I entered the sample directory and built the firmware:

```bash
cd 01-Linux-Development-Toolchain/stm32-linux
make clean
make
```

The build invokes ARM GCC with `-mcpu=cortex-m4 -mthumb`, emits debugging symbols using `-g3`, links with the custom memory map, and converts the resulting ELF into raw binary and Intel HEX images.

| Output | Description |
|---|---|
| `build/stm32_blinky.elf` | Linked firmware image and debugging symbols |
| `build/stm32_blinky.bin` | Raw binary image |
| `build/stm32_blinky.hex` | Intel HEX representation |
| `build/stm32_blinky.map` | Linker-generated symbol and section map |

**Observed repository build, November 1, 2026:**

```text

```

This is the reported size of the specific tested build, not a guaranteed size for other compiler versions or source revisions.

## 6. Program and verify the target

I flashed the generated ELF through the onboard ST-LINK using:

```bash
make flash
```

The Makefile executes the equivalent of:

```bash
openocd -f interface/stlink.cfg \
  -c 'transport select swd' \
  -f target/stm32f4x.cfg \
  -c 'program build/stm32_blinky.elf verify reset exit'
```

OpenOCD identified **512 KiB flash**, programmed the target, verified the written image, and reset the processor:

```text
** Programming Started **
** Programming Finished **
** Verify Started **
** Verified OK **
** Resetting Target **
```

The LED-blinking behavior had already been observed on hardware during the initial bare-metal validation. The Stage 01 repository build subsequently passed the flash-and-verify procedure.

OpenOCD also emitted `Error: timeout waiting for ITM_TCR_BUSY_BIT` during target examination. This did **not** prevent programming or verification. The underlying trace-related cause has not been established; the diagnostic is preserved in [error.md](error.md).

## 7. Debug the target using OpenOCD and GDB

I use two terminal sessions for interactive debugging.

**Terminal A - OpenOCD server:**

```bash
make debug-server
```

**Terminal B - GDB client:**

```bash
make debug
```

The `debug` target opens the ELF in GDB but does not connect automatically. The connection is established from the GDB prompt:

```gdb
 target extended-remote localhost:3333
 monitor reset halt
 break main
 continue
```

Once halted at a breakpoint, the following commands inspect processor state and peripheral registers:

```gdb
info registers
x/8i $pc
x/1wx 0x40020000
x/1wx 0x40020014
```

`0x40020000` addresses `GPIOA_MODER`; `0x40020014` addresses `GPIOA_ODR`. Bit 5 of `GPIOA_ODR` reflects the PA5 output state.

**Validation distinction:** GDB successfully loaded the ELF and resolved a breakpoint at `main` in the earlier debugging session. A successful remote GDB attach and register inspection have not yet been independently recorded. The commands above describe the configured workflow, not an additional claimed test result.

Halting at a breakpoint changes the target's execution timing. For quantitative real-time measurements, nonintrusive instrumentation is preferable to breakpoint-based observation.
